# PwEevee installer — signing architecture and threat model

Date: 2026-10-25 · status of this build: **validation engine shipped; in-browser re-signing not shipped** (every claim below reflects what the shipped code actually does — see §5 and the session report for the capability boundary).

## 1. Goal

Let a user obtain the official PwEevee IPA, supply their own signing credentials, learn
exactly what their credentials allow, and complete every workflow that can be completed
without the IPA site ever seeing the credentials. The privacy requirement is absolute:
the `.p12`, its private key, and the certificate password are processed only in the user's
own browser tab, or not at all.

## 2. What runs where

```
┌ user's browser tab (pweevee.skytweak.dpdns.org, strict CSP, no third-party scripts) ─┐
│  installer.js (website-src/assets/installer.js — self-written, vendored into the repo) │
│  ├ SHA-256 = pure JS, block-chunked over File.slice() — no full-file ArrayBuffer       │
│  ├ ZIP central-directory reader over Blob slices + DecompressionStream('deflate-raw')  │
│  ├ binary-plist / XML-plist parser (own implementation, no dependencies)               │
│  ├ .mobileprovision parser: minimal DER walk → CMS OCTET STRING → plist                │
│  ├ .p12 structural validator (PKCS#12 envelope only — see §5)                          │
│  ├ staged UI state machine: collect → validate → summary → handoff/export/cancel       │
│  └ self-test runner (#installer-selftest diagnostics panel, in-memory fixtures)        │
│  everything reads the user-selected local files; NOTHING is ever uploaded              │
└───────────────────────────────────────────────────────────────────────────────────────┘
                       │  (the only network side effects: none)
static host (PwEevee website) ── serves the page + data JSON previously generated by
update-releases.pl / update-stats.pl from the GitHub API. The hero-download panel links
to the GitHub release asset; the browser downloads it from GitHub directly.
```

- **No backend endpoints exist for the installer.** There is no upload route to accept a
  `.p12`, a password, or a signed IPA. The privacy property is enforced by *absence of
  any endpoint*, not by promises on the page.
- The automated website suite (section 8, `website-tests.pl`) re-verifies continuously
  that `installer.js` contains no `fetch`/`XMLHttpRequest`/`WebSocket`/`sendBeacon`,
  no `localStorage`/`indexedDB`/`document.cookie` writes, and no third-party hostnames.

## 3. Threat model

**Assets protected:** PwEevee users' Apple signing credentials: identity certificates,
private keys, and the passwords that protect them.

**Adversaries considered:**

1. **This website (semi-trusted):** if the site were compromised, it serves any HTML/JS
   it wants to the user's tab. Mitigation is therefore not "trust the site" but:
   x27nothing to steal" if credentials never reach the tab while a compromised tab is
   watching — hence the decision that the *full signing below the browser's own hands
   is done by the operating system's own tools* (AltStore/SideStore/Feather/Xcode) for
   this build, not by our JS. A compromised site cannot exfiltrate what never exists
   in its tab. (Residual: a compromised site could still trick the user — a notice in
   the workshop states the page is a plain static page and the signed artifact should
   always be produced by a locally installed tool the user chose.)
2. **In-page attackers (XSS-style):** impossible per current deployment (static HTML,
   strict CSP, no inline execution, no third-party scripts). The suite's purity audit
   keeps it that way.
3. **User error:** wrong file picked, mismatched profile, expired certificate. Handled by
   the explicit pre-sign summary, three-valued status badges (validated / unsupported /
   unable to verify), and the refusal to represent anything as installed until a tool
   the OS runs reports success.
4. **Chip-in-memory persistence:** the documentation states plainly that clearing
   references in JS cannot guarantee forensic erasure; the user is advised to sign in a
   fresh tab and close it after use. Nothing is stored anywhere by design.

**Out of scope:** trustworthiness of the *unsigned* IPA content itself (that is the
release-verification problem: SHA-256 shown against the GitHub-published value), and any
attempt to defeat Apple provisioning rules (not implemented, not wanted).

## 4. Data flow per stage

| Stage | data | local-only | failure mode |
|---|---|---|---|
| Get PwEevee | GitHub release asset + published SHA-256 (from `releases.json`) | download happens browser→GitHub; user's own SSL tools | panel hides itself if release data is stale; no invented checksum |
| Choose credentials | `.p12` (optional), `.mobileprovision`, IPA already fetched | `File` objects read via slices inside the tab | unsupported file types rejected with reasons |
| Validate | parsed structures | all parsing in-tab; results table built in DOM | three-valued badges; garbled inputs produce `unable to verify`, never invented facts |
| Sign locally | — | **not performed in this build** (§5); on-device tools perform it | the stage explains why and routes to the honest paths |
| Install/export | unsigned/validated IPA; no upload | export via Blob download; AltStore/SideStore instructions | no installation state is ever displayed |

## 5. Honest capability boundary (why no in-tab re-sign shipped)

A full in-browser signer would have to, for *every* Mach-O (main exe, 3 frameworks +
2 injected dylibs, 5 app extensions): decrypt the user's PKCS#12 (PBES1 with PKCS#12 KDF
+ RC2/3DES — WebCrypto exposes none of those primitives for raw use), parse the X.509
chain from DER, generate entitlements + requirements DER, build CodeDirectory v0x20400
with per-page SHA-256 slots, produce a CMS SignedData blob via RSASSA-PKCS1-SHA256,
splice LC_CODE_SIGNATURE (binary resize, aligning all 6 Mach-Os), rewrite
`_CodeSignature/CodeResources`, and every mistake lands as "app did not launch" on a
phone that cannot tell you why. WebCrypto cannot do RSASSA-PKCS1-v1_5 with SHA-256 +
attached detached data in a form iOS accepts without a CMS writer, and rolling one is
exactly the class of code this project refuses to ship unverified.

Decision for this build: **the browser validates and prepares; the signing runs inside
the tool the user already has on-device or on their computer** (AltStore Classic,
SideStore, Feather, Sideloadly, Xcode). Those tools hold the user's credentials locally
already, which satisfies the core privacy requirement (credentials remain local to the
user's device) without a hand-rolled signer the maintainer cannot verify across
signature-format revisions. The boundary is stated to the user in the workshop's
sign stage, not hidden.

Follow-up (documented, not silently promised):vendoring
`PKCS#12 KDF + RC2/3DES`, careful Mach-O-editing on 6 binaries, a full CMS writer, and —
critically — a real-device verification story across iOS 18/26/27 release. Until that
gate is met, the honest path is the tool-supported one.

## 6. Reused verified research

The compatibility matrix builds on the distribution-readiness investigation
([taurus-rc/reports/distribution-readiness.md](../../taurus-rc/reports/distribution-readiness.md)),
which established — with cited Apple/AltStore/SideStore/fastlane sources — the free-team
App-ID budget (main app + 5 appexes → up to 6 App IDs, limit 10/week),
SideStore ≥ 0.6.2 extension-profile reuse, the free-team App Groups limitation (widgets
degrade, not crash), and the sign order (deepest code first).

## 7. Privacy copy obligations (implemented on /install)

- A notice about credentials never leaving the device appears before any file picker.
- The phrase about memory: "closing the tab is the reliable cleanup; clearing in-tab
  references is offered but cannot guarantee erasure from physical memory."
- Support/contact copy explicitly forbids pasting private keys or passwords anywhere.
- The workshop names its own trust posture: static page, no forms, no uploads.
