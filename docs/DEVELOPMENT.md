# Development

How this project is built, who does what, and how releases happen.

## Roles (stated openly)

| Role | Who | What they do |
|---|---|---|
| Direction, review, testing, releases | the human maintainer | decides what gets built and released, tests on device, reviews everything |
| Main coding/build agent | **Freebuff** | repository work, implementation, build automation, testing, troubleshooting |
| Assistant | **ChatGPT** | prompting, planning, troubleshooting, debugging, research assistance |

The maintainer has programming knowledge and participates directly in development.
AI was used as a development tool for this integration project. AI did not create
spoti.pw or EeveeSpotify, and nothing in this project presents it that way.

The website repeats this disclosure on `/development` — it is a permanent, prominent
part of the project, not a footnote.

## Engineering rules

1. **Evidence before code.** Everything the build does is derived from the audit
   (`docs/UNIFICATION-AUDIT.md`): real headers parsed from real packages, load commands
   dumped from the proven binary, byte comparisons — never guesses.
2. **One source of truth per fact.** Load commands and dependency policy live in
   `PwEvevee/dependencies.json`; component provenance in the component `manifest.json` files;
   the audit narrative in `docs/UNIFICATION-AUDIT.md`.
3. **Fail loudly.** Duplicates, missing resources, malformed archives, unexpected
   binaries all stop the build with named errors. Nothing is silently "fixed".
4. **Tests are not negotiable.** `deb-format-test.pl` and `build-tests.pl` must pass;
   when a test fails, fix the cause — never weaken the test.
5. **Byte-exactness where it matters.** The deb generator reproduces the reference
   package's `data.tar.lzma` byte-for-byte; the injector reproduces the proven
   executable's load-command block exactly (ncmds 153, sizeofcmds 16680).
6. **Never touch the reference.** `docs/spoti.pw-builds/` is an *optional local* pristine
   clone (its gitlink entry was dropped in `43a92ce`, so it is not in the repository);
   nothing writes there, nothing builds from it.
7. **No secrets.** No credentials, tokens, certificates or personal data in the
   repository, ever.

## Release process

1. `bash PwEvevee/build-system/unified.sh <input.ipa> -o dist/<name>.ipa` — all validations must pass
2. the maintainer installs and tests the IPA on a device
3. `perl PwEvevee/build-system/release/make-release.pl dist/<name>.ipa dist/build-manifest.json --githash $(git rev-parse --short HEAD)`
4. publish the IPA as a GitHub release — that release is what the website links to
5. `scripts/update-releases.sh` — refreshes GitHub release data and AltSource variant
   data, re-renders every page of `website/` from `website-src/`, and runs the website
   checks
6. deploy: copy `website/` (or just changed files) to the SkyTweak web root — it is
   pages and assets only, no build files

Nothing publishes automatically. Step 2 is a hard gate.

## Editing the website

`website/` is **generated output**. Edit `website-src/layout.html` and
`website-src/pages/*.html`, then re-run `perl PwEvevee/build-system/release/render-site.pl`.
Anything data-driven — versions, dates, sizes, asset lists, release notes, variant
metadata — comes from `website/data/releases.json` or `website/data/altsource.json`
through a `[[component:name]]` placeholder. Adding a hardcoded version to a template
fails `website-tests.pl`.

Local preview: `perl scripts/dev-server.pl 4173` serves `website/` with the same
root-mapped clean URLs as the nginx example.

Release data on its own: `scripts/update-releases.sh --no-render --no-test`. To work
without the network: `scripts/update-releases.sh --offline`.

## Where downloads come from

The website hosts nothing. It presents exactly two kinds of download, and labels which
is which:

| Source | Used for | Generated by |
|---|---|---|
| GitHub releases | PwEevee, spoti.pw and EeveeSpotify releases, notes, dates, assets | `update-releases.pl` |
| SideloadLabs AltSource | the installable EeveeSpotify IPA variants (Standard / Patched, including Liquid Glass) | `update-altsource.pl` |

A download button is only rendered once the release and the asset both exist. When they
do not, the page shows "Download currently unavailable" and offers the release on GitHub
instead. There is no locally built "dev" release and no `website/releases/` payload.

## Retention policy

`WEBSITE_IPA_RETENTION_MONTHS=6` (default) applies to the **local archive only**. At
every release registration, `make-release.pl` removes builds older than the window from
`releases/current/` and flags their cards `past_retention: true`. That keeps the working
tree from growing without bound; it no longer affects the website, which reads GitHub
and never serves a build file itself.

## Commit conventions

The upstream repo uses Release Please with `feat:`/`fix:`/`chore:`/`refactor:`/`docs:`
conventional commits. The unified-build tooling follows the same convention. Never edit
`version.txt` by hand.

## Working on the components

- To re-extract components after obtaining new upstream packages:
  `perl "Evevee Spotify/component/extract-components.pl" --force` (then re-run tests and a full build)
- To change the load-command set (e.g. a future upstream version needs different
  commands): edit `PwEvevee/dependencies.json` and update the audit + tests to match;
  never edit the injector's command list ad hoc
- To change packaging: `PwEvevee/build-system/package/make-deb.pl` / `make-ipa.pl`; run the format
  tests; if the change alters observable output, prove it against a reference package
  the way the audit did (member-for-member byte comparison)

## Continuation

If the current maintainer stops, this repository plus the applicable upstream licenses
is the starting point: the components carry their provenance, the docs explain every
decision, and the tests define "correct". A continuation must preserve upstream
licenses, copyright notices, attribution, and requirements — see the website's legal
page for what that does and does not permit.
