# On-visit freshness: what happens when someone opens the website

This documents the release-freshness contract for every page of the website:

- what runs on a visit, what is cached, and what never runs again too soon;
- what the browser may touch and what it may never touch;
- what fails-open when the network is broken;
- which data sources are authoritative and how each of them stays current.

It is the reference implementation note for the `freshSession` module in
`website-src/assets/pweevee.js` and the check layer of
`PwEvevee/build-system/tests/website-tests.pl` (section headed
"on-visit freshness check").

## The three freshness layers

| Layer                 | What it refreshes                                     | When it runs                                  | Credentials |
|-----------------------|-------------------------------------------------------|-----------------------------------------------|-------------|
| **Render**            | Releases, AltSource variants, download links, SHA-256 | Site build (manual or update scripts)          | none needed |
| **Scheduled refresh** | Repository statistics + rendered site                 | Every 15 min in CI (`update-stats.yml`)        | `GITHUB_TOKEN`, server-side only |
| **On-visit check**    | Visible version/date text of a rendered release       | Once per browser session, per page opened      | none — anonymous |

The render layer is the only thing that decides what a download button offered,
what a SHA-256 line says, and what the AltStore source contains. The on-visit
check never changes any of those; it can only tell the visitor that a *newer*
release exists upstream, by updating a version label and linking to the
authoritative GitHub release.

## What a visit does, exactly

1. Any page opens. Its markup was rendered earlier from
   `website/data/releases.json`, which the scheduled refresh regenerates.

2. Once JavaScript is free, the `freshSession` module in `pweevee.js` collects
   the pages' render-time hooks:

   - `data-release-panel="owner/repo"` + `data-release-epoch` +
     `[data-release-version]` on full release panels;
   - `data-fresh-repo="owner/repo"` + `data-fresh-kind` (version | date) +
     `data-fresh-epoch` on individual version/date facts.

3. A session gate runs first: if this browser has *already* completed a full
   check within the last 10 minutes (recorded in sessionStorage, key
   `pweevee-fresh`), the page does nothing else — clicking between pages does
   not pile up upstream requests.

4. Otherwise, for each distinct repo on the page, exactly one anonymous
   request is made to the public reads-only endpoint:

   `https://api.github.com/repos/<owner>/<repo>/releases/latest`

   with `credentials: 'omit'`, no Authorization header, no token, no cookies,
   no analytics, no resource-cache reuse (`cache: 'no-store'`). Repos are
   URL-encoded through `encodeURIComponent`. Nothing is ever uploaded or
   "checked in".

5. A payload is acted on only when all of this holds:

   - it parses as JSON with a `tag_name`;
   - it is not a **draft** release;
   - its `published_at` epoch is **newer** than the epoch that was rendered.

   When those hold, the visible text is updated *in place*, without a
   re-render and without touching anything else:

   - a version fact becomes the new tag name (leading `v` stripped to match
     the rendered convention);
   - a date fact becomes `Released <day month year>` in the same human format
     the renderer uses;
   - a full release panel gets its version updated plus one additional badge
     linking to `rel.html_url` — that is the honest story: the offer on the
     page was the render-time offer, and the badge takes the visitor to the
     authoritative place for whatever is newer.

6. The footer note (`[data-fresh-note]`) is annotated with a
   `data-fresh-state` attribute and a `title` explaining what just happened.
   The rendered site root gets `data-fresh="checked"` or
   `data-fresh="offline"`.

## What is cached, and for how long

| Cache                       | Key                  | Lifetime |
|-----------------------------|----------------------|----------|
| sessionStorage `pweevee-fresh` | one browser tab session | cleared when the tab closes; gates the whole check for 10 minutes after a completed full pass and gates each repo for the same window |
| Server-rendered release data (`releases.json` → HTML) | none needed | regenerated by the scheduled update cycle |
| `/data/*.json` on the CDN   | URL                  | 5 minutes (`Cache-Control: public, max-age=300`) |
| `/assets/`                  | name                 | 24 hours, fingerprints deliberately *off* so an update rolls out predictably |

The AltStore/SideStore source JSON itself is **not** rebuilt by a page visit.
It is a signed-off build artifact produced by the release-triggered workflow
`appsource-update.yml`, which runs `update-appsource.pl` on each real release
publication, verifies each IPA end-to-end (SHA-256, Info.plist facts,
bundle identifiers, host Spotify build), validates the produced source against
the AltStore/SideStore schema, and commits **only** the source files when they
actually changed, atomically, with `contents: write` as the only permission.
A release whose verification fails never overwrites the published source.

## How failures are handled

Any of these leaves the page **exactly as rendered** — the rendered version,
the date, the download links, the SHA-256 lines: they were verified at render
time and remain internally consistent:

- network offline, DNS failure, CORS block;
- HTTP error, including 403 rate-limit (unauthenticated requests are capped
  by GitHub per-IP; several pages open in different tabs share one 10-minute
  window, so a burst of visits still only produces one request per repo);
- a payload that is not the expected shape, or a draft release.

The UI communicates this once, quietly:

- `<html data-fresh="offline">`;
- the footer note dims and explains in a tooltip that the re-check could not
  reach GitHub and the rendered data is the most recent verified snapshot;
- the last-known-good rendered values stay on screen; nothing flashes, no
  panel rebuilds, no request retries in a loop.

A single repo failing does not mark the whole page offline: the check settles
per repo, and only repos that answered with anything are updated.

## Authoritative sources

| Fact                              | Authoritative source                             | How it is refreshed |
|-----------------------------------|--------------------------------------------------|---------------------|
| Latest published release, versions, dates, notes | GitHub Releases API (write path: `update-releases.pl`) | scheduled update cycle + release publishes |
| Download URLs and SHA-256         | GitHub release assets (verified at build/render time) | the render layer, never the browser |
| AltStore/SideStore source JSON    | `update-appsource.pl`, from verified IPA facts     | release-triggered workflow only |
| Repository stars/forks/downloads  | GitHub API (aggregate stats)                       | 15-minute scheduled workflow |
| AltSource variants for EeveeSpotify | SideloadLabs published AltSource (read-only)      | scheduled update cycle |

## What the browser may never do

Even when a fresher release is detected, the client-side code never:

- invents, rewrites or replaces a download URL;
- rewrites or hides a SHA-256 line;
- marks a release as "verified" or "signed" from a browser-side guess;
- sends any data anywhere, shares any token, or reads any cookie;
- assumes an AltStore deep link for a version it did not see in render data.

Those all change only when new render data ships. This is what makes it safe
for thevisitor's browser to re-check anything at all: it can only learn and
report, never decide.

## Test coverage

`PwEvevee/build-system/tests/website-tests.pl`, the section headed
"on-visit freshness check", asserts (among others) that:

- rendered panels, version headlines and date facts all carry the hooks;
- the module asks exactly one endpoint, derived from hook data, never
  hardcoded to a repo string;
- the session gate and the 10-minute repo window are present;
- `credentials: 'omit'` is in the request, and no Authorization header,
  token or secret appears in the module at all;
- download URLs and hash lines are never rewritten from browser-side data;
- drafts are rejected, and failures degrade to the rendered values.

The rest of the suite (4410 checks) already covers data shape, AltSource
schema, download-target integrity and secrets scanning.
