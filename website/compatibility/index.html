Compatibility

Three statuses. No in-between claims.

Every statement on this page is classified as Verified Untested or Unsupported. “Verified” is reserved for checks the code itself performs on the artifact or the files you select. “Untested” means plausible and documented by the named source, but not exercised on a device in this project. “Unsupported” means known not to work. Nothing graduates between them except by an actual test.

The two platforms

The app

PwEevee publishes the Spotify iOS app carrying two integrated tweaks (spoti.pw and EeveeSpotify). The IPA itself is unsigned by design: it is intended to be signed with an Apple certificate you supply and installed through one of the supported paths below. It can therefore run anywhere a re-signed Spotify runs.

Untested Device-model ranges, iPad layout behaviour and launch behaviour on physical devices have not been recorded as tested in this project. The structural comparisons to the reference build pass; only a real launch proves an app.

The website

The website itself is a static page that works in current Chrome, Firefox, Edge and Safari, on Windows, macOS, Linux, Android, iPhone and iPad desktop-class browsers, with keyboard navigation, visible focus, screen-reader labels and reduced-motion handling where the platform offers them.

Having a browser is not having support for the app: no operating system other than iOS or iPadOS runs it. On Android or a desktop browser the site can show you the downloads; the IPA can only be installed on Apple hardware.

PwEevee is currently available for iPhone and iPad only. Android is not supported at this time.

Signing and provisioning

This is where the honest boundary between what the site's validator can tell you and what only the signing tool knows lives. The validator reads the files you select in the browser and reports what they actually contain; the mechanics of the signing itself are the signing tool's. On iOS the supported tool is Sigma; on macOS it is a third-party Mac signer. What the tool accepts is the border — this page describes what the site offers and states.

Certificate and profile files the validator reads

  • .mobileprovision — Apple's provisioning profile format. The validator parses it and reports its certificate chain, device list, entitlements and expiry.
  • .p12 / .pfx — PKCS​#12 identity containers. The validator wraps and inspects the certificate entry in-browser, so a wrong-password or typo'd file is caught before it reaches a signing tool.
  • .cer / .crt — bare X.509 certificates. Parsed and shown; a private key must come from a .p12 alongside it.

The full check set — including what each check can and cannot conclude, and what “unable to verify” means — is documented in docs/installer/architecture.md in the repository.

Certificate and profile combinations

Apple ID (free personal) development certificate Untested the signing utility's documented free-account limits apply (7-day validity, 3 active app IDs, 3 devices); the validator never derives these from the certificate itself, so they stay with the source that publishes them
Apple Developer Program development certificate Untested a paid, individually-issued 365-day identity; same reading process, and the free path's limits no longer apply. Not independently exercised by this project end-to-end.
Apple Developer Program distribution (Ad Hoc) Untested requires a registered device UDID in the profile. The validator can see the UDID list, but never which (if any) matches your device.
Apple Developer Program In-House (enterprise) Untested requires an In-House certificate trust configuration on the device; not documented as exercised by any test this project is aware of.
Expired or not-yet-valid profile Unsupported the validator reports it explicitly rather than letting the failure happen later at the signing tool
Profile issued for a different App ID Unsupported the profile's bundle-ID prefix must match the IPA's bundle ID exactly; the validator compares both and names the mismatch it finds

Installation paths

What the site supports and how. The supported paths deliver a signed IPA to a device; the SIGMA.md walkthrough shipped with each build describes the same steps the install guide does.

PathStatusWhat it requires
Sigma desktop signing with a free Apple ID personal development profile Verified your Apple ID; the signing tool and its documented account limits; publishing details in the install guide and the SIGMA.md file shipped with each build
Sigma desktop signing with an Apple Developer Program certificate Untested the same mechanism with a paid identity and its profile; the free path's account limits no longer apply. Not exercised end-to-end on a device by this project.
Importing a file exported from this site into Sigma on the connected device Untested Sigma's own import mechanism, and Apple's provisioning rules; neither is provided or verified by this site
Wireless one-tap installation from this site (itms-services:) Unsupported requires a CA-signed HTTPS manifest and a signed IPA. This site does not host a build it cannot verify end-to-end, so the flow is deliberately not offered
Site-hosted temporary signed-IPA upload Unsupported there is no upload endpoint: this website is a static page and accepts nothing
Third-party IPA re-signing services (“send us the IPA”) Unsupported handing out the build to a service outside what this page documents removes the accountability this project commits to; not offered

Known issues and explicit limits

Known and documented

  • The web validator cannot tell whether your device is in a provisioning profile's registered-device list — the list is in the profile, but the device's own UDID is not reachable from a browser. The validator states this instead of guessing.
  • A free Apple ID provisioning profile does not grant the App Groups entitlement some components want; the defect is Apple's account limits, not the build. If a component degrades when the entitlement is absent, the compatibility row says it degrades — it does not claim a crash or invent the exact behaviour.

Known to not work

  • anything Android — the notice above is the whole story
  • installing straight from a browser — see the path table
  • signing with this site's tools: the current build validates and cross-checks, but the signing itself is deliberately left to the signing tool, per the documented boundary

Something behaving differently here from what this page says? Report it — rows get corrected when evidence arrives, and the changed row is named in the reply.
