Before you file: the order worth checking

These five checks in order resolve most of what gets reported here. If a check fails or cannot be completed, that failure is exactly what a good report documents — with the check named.

  1. Verify the file you have. Compare the SHA-256 of your download against the value published on the downloads page, computed from the exact published bytes. A mismatch means the file is not the released artifact — that alone rules out every signing step below.
  2. Check credentials freshness. A profile past its expiry date, or a certificate that has expired, fails at signing time. The install guide's validator reads exactly the files you would use and reports validity dates, before any signing tool is involved.
  3. Confirm the App ID matches. The bundle identifier inside the IPA and the identifier the profile was issued for must match exactly. The validator cross-checks this and names the mismatch if there is one.
  4. Sign, don't re-inject. One build already carries its two integrated tweaks and their dependencies — no extra injection is needed, and adding it corrupts the app. Use a signing tool in sign-only mode on this IPA.
  5. Then launch. If the app still fails to start after a clean sign of a verified file on a compatible iOS version, gather what the report needs and file it with the signing tool's own error text — not just "it didn't work".

Known issues, kept in front of the file-a-bug link

  • Free Apple ID accounts: 7-day expiry and the active-app cap mean re-signing is routine, not a failure.
  • Free profiles do not grant the App Groups entitlement some of a Spotify app's supporting components use; affected components degrade and the app itself still runs.
  • The installed artifact is structurally validated and compared byte-for-byte against a reference build, but physical-device launches are not test results this project has recorded — see compatibility.
  • The site's cached badge means the last GitHub API read failed and the last known-good value is being shown deliberately — see the FAQ.
  • The upstream currently lacks a localization pane; it is known upstream work, not a PwEevee regression, and belongs with its own author.

What a report should include

Include

  • The release version label (shown on the release), and the Spotify version the build pairs with, from the build manifest if it matters.
  • Expected and actual behaviour, in one sentence each.
  • Steps to reproduce, as you actually performed them — including the Apple device it was attempted on, the iOS version and the signing tool and version used.
  • The relevant validator output (profile validity, App ID cross-check) when the problem is at the credentials stage.
  • The signing tool's exact error text, when the problem is at sign or install time.

Never include

  • Your private key, a .p12 file, or any file containing one.
  • Your certificate password or any passphrase.
  • A provisioning profile that contains device identifiers you do not want public — redact them from the payload and say they were redacted in the report.
  • Personal files, screenshots containing account data, or anything you would not post publicly — GitHub issues are public the instant they are filed.

This page and the install guide both say the same thing: nothing that identifies your signing identity or any password belongs in a bug report, support ticket, or chat. If you have already posted such a credential publicly, rotate the certificate and revoke the profile first, then report the incident — the rotation is the fix that matters.

Not the right audience

Spotify the app

Account, billing or official-app problems go to Spotify. This project has no connection to Spotify AB.

Upstream tweak behaviour

Feature requests or bugs in the way spoti.pw or EeveeSpotify behave as apps belong to their own repos — Credits names them.

SideloadLabs IPA variants

Those variants come from SideloadLabs' own AltSource — install problems with those files belong with SideloadLabs, not this project.

No issue tracker account? Every route on this site works without one, and the contact page lists how to reach the maintainer for anything that genuinely does not fit an issue, including rights-holder requests.
