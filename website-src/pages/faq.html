FAQ

The questions this project actually gets.

Every answer here is backed by a page or document on this site — nothing is answered with a promise. If your question is not here, support has next steps.

What is PwEevee?

An independent integration, build and distribution project. It takes Spotify's iOS app, integrates two upstream tweaks — spoti.pw and EeveeSpotify — validates the result structurally, and publishes it as an unsigned IPA through GitHub releases with the exact SHA-256 of every published file. It did not create Spotify or either tweak.

Is PwEevee affiliated with Spotify, Apple, or the upstream projects?

No. PwEevee is not affiliated with, endorsed by or connected to Spotify AB, Apple Inc., spoti.pw, EeveeSpotify or SideloadLabs. Spotify and Apple trademarks belong to their owners. The upstream tweaks are separate projects with their own authors and licenses — see Credits and Legal.

Which platforms does it run on?

iPhone and iPad — iOS and iPadOS only. The website itself works in any modern browser on Windows, macOS, Linux, Android, iPhone and iPad, but a browser is not a place an IPA can run.

PwEevee is currently available for iPhone and iPad only. Android is not supported at this time.

Why is the build unsigned?

A signed app is tied to whoever signed it. PwEevee publishes the build unsigned so that you sign it with your own Apple certificate: the identity your device will trust belongs to you, not to this project, and requires no permission from it. The install guide walks through the signing step with the tool that holds your credentials. This is also why the site has no enterprise distribution: an unsigned IPA cannot be installed over a network without a distribution mechanism the project deliberately does not operate.

Does a SHA-256 checksum mean the app is safe?

No. A checksum proves the file you received is byte-for-byte the file the release published — nothing more and nothing less. It says nothing about whether the app does what you expect, does not contain bugs, or will pass Apple's review. Verify the checksum when transferring files between machines; judge the app separately.

Where do the download links go?

Straight to the source that publishes the file, every time: GitHub release assets for PwEevee's own builds and the upstream projects' releases, and — labelled separately, because it is a different kind of thing — the variant IPAs the SideloadLabs AltSource lists for EeveeSpotify. Nothing is served from this site's own disk, and a download button only renders when the release data says an asset actually exists. Where one does not, the page says so instead of showing a dead button.

Where do the statistics come from?

The homepage stats band reads website/data/stats.json, a snapshot produced by the project's update script from the GitHub API. The browser never calls GitHub. The snapshot is refreshed on an hourly schedule and the page shows when it was last generated. Numbers you see are GitHub's counts: stars, forks, real watchers (subscribers_count), open issues and pull requests, and release asset downloads. Those download totals are asset-download counts — not unique users, devices, or successful installs — and no statistics of that last kind exist here, because nothing measures them.

What does the “cached” badge mean?

It appears on a release card when GitHub could not be reached during the last update run. The site deliberately shows the last known-good release information instead of an error or an invented state, and the badge is the honest marker that this value may be stale. Nothing is edited by hand to hide it — if GitHub is down for you, it was down for the updater too. A 403/429 in the update logs is the anonymous API rate limit; 451 means a repository has been disabled upstream, which is a real state, not a bug.

Can the site sign or install the IPA for me?

No — and the install guide is explicit about why. The browser-side validator reads the files you select (IPA, provisioning profile, certificate container) directly in your tab and cross-checks them against the release, but it never signs. The signing step belongs to the tool that holds your certificate on your device, where the private key belongs in the first place. There is no upload endpoint for any of it: this is a static site with no server code behind it.

I don't have a paid Apple Developer account. Can I still install?

Yes — the signing tools support a free Apple ID personal-development flow, with documented limits: 7-day app validity, a cap on active app IDs and devices, and a weekly provisioning budget. Re-signing before expiry becomes a routine. The compatibility page keeps these rows marked “untested” rather than “verified”, because the limits are the signing tool's and Apple's documented behaviour, not something this project's validator derives.

Where are the older releases?

On the GitHub releases page for the repository, permanently, as long as GitHub hosts them. The release centre shows the same chronological history up-to-date from the most recent API read, with prereleases and drafts labelled as such; no permanent availability of any hosted build is promised anywhere on this site.

Why does the site never say “installed successfully”?

Because nothing in a web page can observe an app installation. The operating system confirms a launch on-device; the signing tool confirms a signature. A browser tab can structurally validate an IPA and tell you what a profile permits, and stops there. The install guide's last step hands the artifact to the tool that will actually perform the installation and report its own success or failure — and the website does not foresee outcomes it has no way to measure.

How do I report a bug?

On the project's real issue tracker, via Support. The support page lists what a report should include and what must never be included — most importantly, never your private key, certificate password, or any file containing either.

Where is everything else documented?

In the repository, and indexed on the documentation page: the installer architecture, the certificate/profile compatibility matrix, the deb packaging notes, the build and validation suite and the development process. On-site pages — install, releases, compatibility, privacy, security — cover what a visitor actually needs.
